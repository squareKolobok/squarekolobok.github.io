Runtime Async в .NET. Что изменилось

29 октября 2026 г.

Привет, сегодня затронем тему, что изменилось в асинхронности в .net. Когда в C# 5.0 завезли ключевые слова async и await, это была настоящая магия. Нам разрешили писать сложный асинхронный код так, будто он обычный линейный и синхронный. Но за эту магию компилятору и рантайму все эти годы приходилось расплачиваться тоннами скрытого кода под капотом.

В новых версиях платформы эта история переписывается с нуля. Разработчики выкатили, пожалуй, самое масштабное архитектурное изменение за последнее десятилетие — Runtime Async. Суть логики проста: асинхронные паузы и переключений полностью перенесли со стороны компилятора на сторону райнтайма.

Давайте разберем, как эта штука устроена, и как рантайм теперь выполняет асинхронный код.

🛠 Как это было раньше (и работает сейчас)

Компилятор, когда видел слово async в определений метода, он генерировал машину состояний (IAsyncStateMachine), а не просто компилировал метод, как он есть.

Во что превращался код

public async Task<int> CalculateAsync(int x)
{
    int y = x + 10;
    await Task.Delay(100);
    return y * 2;
}

После компиляции этот метод превращался в синхронный метод, который инициализировал ту самую машину состояний:

public Task<int> CalculateAsync(int x)
{
    <CalculateAsync>d__0 stateMachine = new <CalculateAsync>d__0();
    stateMachine.<>4__this = this;
    stateMachine.x = x;
    
    stateMachine.<>t__builder = AsyncTaskMethodBuilder<int>.Create();
    stateMachine.<>1__state = -1;

    stateMachine.<>t__builder.Start(ref stateMachine);
    return stateMachine.<>t__builder.Task;
}

Вся логика первоначального метода уходила в метод MoveNext() этой структуры, где компилятор строил switch-case или if-ы для переключений состояний:

void IAsyncStateMachine.MoveNext()
{
    int num = this.<>1__state;
    int result;
    try
    {
        TaskAwaiter awaiter;
        if (num != 0)
        {
            // ДО первого await
            this.y = this.x + 10;
            awaiter = Task.Delay(100).GetAwaiter();
            if (!awaiter.IsCompleted)
            {
                this.<>1__state = 0; // Запоминаем, где остановились
                this.<>u__1 = awaiter; // Запоминаем, для того, что бы забрать результат
                
                // Упаковываем контекст выполнения и регистрируем callback
                this.<>t__builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
                return; // Поток освобождается и уходит в пул
            }
        }
        else
        {
            // Сюда мы возвращаемся, когда Task.Delay отработал
            awaiter = this.<>u__1;
            this.<>u__1 = default(TaskAwaiter);
            this.<>1__state = -1;
        }
        
        awaiter.GetResult(); 
        result = this.y * 2; // После await
    }
    catch (Exception exception)
    {
        this.<>1__state = -2;
        this.<>t__builder.SetException(exception);
        return;
    }
    this.<>1__state = -2;
    this.<>t__builder.SetResult(result);
}

В чем были главные проблемы:

  • Бойлплейт код: Каждый async-метод скрывал под собой сгенерированную машину состояний, увеличивая бинарники.
  • Нагрузка на GC: Нужно было обслуживать сгенерированные машины состояний, хранения контекста выполнения.
  • Тяжело читаемые стек-трейсы: При падении ошибки логи были забиты мусором из MoveNext() и TaskAwaiter.

⚡ Как это работает теперь:

В новой модели компилятор C# больше не генерирует машину состояний. Он оставляет метод линейным, размечая в IL-коде низкоуровневые точки ожидания.

Всю магию переключения берет на себя JIT-компилятор и ядро рантайма. Программа теперь компилируется как единый сплошной кусок кода. Ниже посмотрим, как теперь выполняется поток асинхронного кода. Процесс приостановки и возобновления выглядит так:

1. Встречаем await (Уход на паузу)

Thread выполняет метод и доходит до await. Если задача еще не завершена, например, база данных еще не ответила, тогда рантайм мгновенно делает слепок текущего состояния:

  • Создается нативный фрейм паузы (Suspend Frame): Это небольшой блок памяти, который рантайм выделяет из своего нативного пула.
  • Замораживаются регистры процессора: Все локальные переменные, которые в этот момент лежали прямо в регистрах процессора (RAX, RBX и т.д.), аккуратно копируются в этот фрейм.
  • Запоминается адрес возврата (Resume Address): JIT-компилятор знает точный адрес следующей процессорной инструкции сразу после await. Этот адрес тоже записывается во фрейм.
  • Thread свободен: Текущий поток делает обычный физический return, выходит из метода и возвращается в общую очередь пула заниматься другими задачами.

2. Задача завершилась

Когда асинхронная операция завершается, пул потоков выделяет свободный thread для продолжения работы.

  • Этот thread берет сохраненный нативный фрейм паузы.
  • Восстановление контекста: Он загружает данные из фрейма обратно в регистры процессора. Для процессора ситуация выглядит так, будто локальные переменные никуда и не исчезали.
  • Прямой прыжок: Этот thread считывает из фрейма адрес возобновления и делает низкоуровневую процессорную команду JMP (прыжок) прямо на этот адрес.

В этот же момент наш thread оказывается ровно на следующей строчке после await. Никаких проверок состояний, никаких обходов через switch. Это прямой, чистый прыжок на уровне команд процессора.

Концептуально код в рантайме теперь выглядит так:

public Task<int> CalculateAsync(int x)
{
    int y = x + 10;
    var awaiter = Task.Delay(100).GetAwaiter();
    
    if (!awaiter.IsCompleted)
    {
        // Рантайм сохраняет регистры CPU 
        // и адрес следующей инструкции в Suspend Frame:
        Runtime.SuspendAndRegisterContinuation(awaiter); 
        return; 
    }
    
    // Точка автоматического возобновления (Resume Point). 
    // Поток Б прыгнет прямо сюда по команде JMP.
    return y * 2; 
}

🔥 Что нам это дает на практике?

  1. Хорошая экономия памяти: Меньше сгенерированного IL-кода — меньше размер скомпилированного бинарника.
  2. Комфортный дебаг: Точки останова (breakpoints) работают нативно, а профайлеры больше не сходят с ума.
  3. Более эффекттвный механизм асинхронности: Происходит меньше затрат на обслуживание машин состоянии.
