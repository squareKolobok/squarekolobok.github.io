OpenAI API

02 ноября 2026 г.

Всем привет, с вами колобок. Сегодня я решил разобраться, как отправлять запросы в LLM. Сильно вдаваться в подробности не хочу, поэтому будет отправляться только текст, без файлов. Первое, что я узнал - очень часто используют OpenAI API для совместимости и упрощения работы. При желании можно работать с конкретным api определенного поставщика, но если такой задачи нет, то используют для упрощения режим OpenAI Compatible.

Формат запроса

Вот мы подошли к формату запроса. Начнем с авторизации. Обычно авторизация происходит через Bearer токен, хотя тоже может отличаться у некоторых поставщиков - читайте их документацию перед работой.

Запросы отправляются на эндпоинт - /v1/chat/completions.

А теперь взглянем на формат запроса в минимальном виде:

{
  "model": "llm-model-name",
  "messages": [
    {
      "role": "user",
      "content": "Как пройти в библиотеку?"
    }
  ]
}

Где model - название модели из списка доступных messages - список вопросов-ответов с указанием от кого.

В схеме от OpenAI я нашел 5 ролей: system, user, assistant, tool, developer. Если есть желание, можно посмотреть в их репозитории, там указаны json схема и open api файл.

Возможно, самые внимательные уже догадались, как происходит работа - LLM не хранит у себя информацию о сообщениях чата, она получает их с каждым новым запросом генерации текста. Лично для меня это было открытием и после этого я по новой взглянул на их работу. Возможно это лично я привык, что данные у них есть, они уже отправлялись, почему бы и не хранить их, но это ложится на плечи того, кто отправляет запросы. И так же тут можно проследить лимит контекстного окна для LLM - большой ответ забьет пространство на следующий вопрос.

Давайте теперь погрузимся чуть глубже в формат запроса:

{
  "model": "llm-model-name",
  "messages": [
    {
      "role": "system",
      "content": "Ты — крутой ИИ-помощник, отвечай полезно, бесполезно не отвечай."
    },
    {
      "role": "user",
      "content": "Как пройти в библиотеку?"
    },
    {
      "role": "assistant",
      "content": "Все очень просто - открой карты, вбей \"библиотека\" в поиск и иди по указанному пути."
    }
  ],
  "temperature": 1.0,
  "max_tokens": 1024,
  "max_completion_tokens": 1024,
  "stream": false,
  "tools": []
}

Где temperature - параметр креативности от 0 до 2. Чем выше, тем больше креативность и шанс получить бред. max_tokens - максимальное число токенов на генерацию, после чего ее ответ будет остановлен. Есть еще этот же параметр, но с названием max_completion_tokens. Он считается новее, т.к. обрезает генерацию с учетом скрытых токенов. stream - нужно получать ответ по частям или весь сразу tools - список инструментов, доступных агенту с описанием работы. Именно они используются агентами для взаимодействия со всем окружением.

Стоит сказать, что вместо temperature можно указать reasoning.effort - уровень размышлений, если они есть у запрашиваемой модели. Как сказано в документации OpenAI этот параметр несовместим с температурой, только если не выбрано none. Возможно это касается только последних моделей OpenAI и у других провайдеров оно работать будет. Возможные варианты: none, low, medium, high, xhigh, max.

Давайте чуть подробней остановимся на отличии max_tokens от max_completion_tokens. Первый отвечает за максимальное число токенов в ответе. Второй за максимальное число потраченных токенов. Некоторые модели могут включить процесс размышления, в котором не будут возвращать ответ, но будут тратить токены - это ключевая разница. Можно указать max_completion_tokens очень низким и все токены потратятся на размышление, без возврата ответа. Можно указать max_tokens и потратить на генерацию ответа больше токенов, чем в нем указано. Это все стоит помнить и учитывать при работе с LLM.

Теперь немного погрузимся в tools, но поверхностно. В первую очередь это интересно агентам, для взаимодействия с окружением. Тут находится список функций, с их описанием и названием параметров, которые может вызвать LLM. В каждой функции есть название, описание, параметры. Я бы тут обратил внимание, что чем больше функций - тем больше они будут забивать контекст LLM. Если ставить много MCP-серверов в агент, то можно забить ему контекст запроса ненужной информацией.

Пример функции:

{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Получить текущую погоду",
        "parameters": {
            "type": "object",
            "properties": {
                "location": {"type": "string", "description": "Город"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["location"]
        }
    }
}

Можно еще упомянуть параметр "response_format": { "type": "json_object" } - отвечает за возвращаемый формат ответа, в данном случае json. Указывается в теле основного запроса, но настоятельно рекомендуется в таких случаях указывать и в запросе информацию, что нужен структурируемый ответ.

Формат ответа

Теперь посмотрим на ответ.

{
  "id": "generated-id1",
  "object": "chat.completion",
  "created": 1761465600,
  "model": "llm-model-name",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "reasoning_content": "Новый запрос, пора работать",
        "content": "Все очень просто - открой карты, вбей \"библиотека\" в поиск и иди по указанному пути.",
        "refusal": null,
        "tool_calls": null
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 24,
    "completion_tokens": 11,
    "total_tokens": 35,
    "prompt_tokens_details": {
      "cached_tokens": 0,
      "created_cache_tokens": 0
    },
    "completion_tokens_details": {
      "reasoning_tokens": 0
    }
  }
}

Разберем поля чуть подробнее:

  • id - id генерации. Произвольное значение, при каждом вызове новое.
  • object - всегда chat.completion
  • created - время генерации
  • model - модель, которая генерировала ответ
  • choices - ответы. Чаще всего один, на них подробнее остановимся ниже
  • usage - информация о статистике по токенам. Полезна для получения информации о затратах, объеме контекстного окна

Там есть и другие поля, но они менее интересны, поэтому тут разбирать их не буду.

Описание choices

Теперь внимательнее посмотрим на choices - можно обратить внимание, что это список вариантов ответа. Хотя чаще всего приходит один. Теперь что находится в нем:

  • index - индекс варианта ответа, начинается от 0
  • role - указывает, кто ответил, всегда assistant
  • content - Текст ответа. Возможно значение null при вызове инструментов
  • reasoning_content - Текст рассуждений до генерации. У OpenAI нет его в выводе, Может быть null
  • refusal - Текст отказа, если модель отказалась генерировать ответ.
  • tool_calls - массив для вызова функций агентом. Тут может быть и function_call, разница в числе функций для вызова. Первый способен отправить несколько функций для вызова. Второй только одну.
  • finish_reason - причина завершения генерации.

Описание finish_reason

Тут возможно несколько причин:

  1. stop — модель закончила генерацию сама
  2. length — достигнут лимит выходных токенов
  3. tool_calls — модель просит вызвать функцию, нужно выполнить её и сделать второй запрос
  4. function_call - аналог tool_calls, зависит от того, что поддерживает LLM
  5. content_filter — сработала фильтрация контента
  6. null — генерация ещё не завершена, актуально для стриминговой генерации

Описание usage

Поле может отсутствовать, по хорошему это нужно проверять. Как было сказано, поле используется для получения информации о генерации: лимит токенов, затраты и все отсюда вытекающее.

Поля:

  • prompt_tokens - количество токенов входного запроса
  • completion_tokens - количество сгенерированных токенов
  • total_tokens - сумма prompt_tokens и completion_tokens
  • prompt_tokens_details.cached_tokens - количество токенов, загруженных из кеша
  • prompt_tokens_details.created_cache_tokens - количество токенов, загруженных в кеш. У самого OpenAI его нет
  • completion_tokens_details.reasoning_tokens - токенов, потраченных на размышления

Стриминг ответа

Все выше сказанное больше относится к выключенному стримингу ответа. При стриминге же ответ делится на чанки и часть полей просто записывается в null: finish_reason и usage для примера. Они получают значения только к концу ответа.

Сам стриминг выглядит примерно так:

data: {"id":"generated-id1","object":"chat.completion.chunk","created":1761465600,"model":"llm-model-name","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"id":"generated-id1","object":"chat.completion.chunk","created":1761465600,"model":"llm-model-name","choices":[{"index":0,"delta":{"content":"Прив"},"finish_reason":null}]}

data: {"id":"generated-id1","object":"chat.completion.chunk","created":1761465600,"model":"llm-model-name","choices":[{"index":0,"delta":{"content":"ет!"},"finish_reason":null}]}

data: {"id":"generated-id1","object":"chat.completion.chunk","created":1761465600,"model":"llm-model-name","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"usage": { ... }}

data: [DONE]

Ключевые моменты:

  1. Новые данные приходят в отдельном json, по формату выше
  2. Каждая строка с данными начинается с data
  3. Большинство полей большую часть времени принимает null
  4. finish_reason приходит только в последнем ответе
  5. data: [DONE] - может не прийти, зависит от провайдера LLM
  6. usage может не прийти в последнем чанке, тоже зависимость от провайдера LLM
  7. Ответ находится не в message, а в delta
  8. Для получения текста ответа - нужно склеивать content и размышления, если есть

Промежуточные мысли

Глядя на все, что указано, мне приходит в голову простая мысль - кто-то забил на версионирование api, хотя и указал это в url.

Если с форматом ответа еще не так много проблем - можно игнорировать неизвестные поля, перезаписывать значения из одних полей в другие, то с форматом запроса проблем больше. OpenAI может вернуть ошибку, если отправишь несуществующие поля в json. Другие поставщики тоже могут отправить соответствующую ошибку.

После таких наблюдений начинаешь проникаться еще большим уважением к тем, кто поддерживает агентов для разных поставщиков.

Практический опыт

Пришла пора посмотреть практический опыт работы через api на ❤️net.

Начнем с моделей запроса:

public class Body
{
  public required string Model { get; set; }
  public required Collection<Message> Messages { get; set; }
  public bool Stream { get; set; }
}

public class Message
{
  public required string Role { get; set; }
  public required string Content { get; set; }
}

Дальше создадим модели для ответа:

internal class Response
{
  public Collection<Choice> Choices { get; set; } = [];
}

public class Choice
{
  public Message? Message { get; set; } //для запроса при stream = false
  public Message? Delta { get; set; } //для запроса при stream = true
}

Получать информацию об индексе, смотреть число ответов и тому подобное не будем для простоты. Только посмотрим как происходит работа.

Теперь создадим класс для отправки запросов:

public class OpenAiClient
{
  private List<Message> messages = new(); // история общения

  //Часть полей отсутствует для сокращения объема

  public async Task<string> GetAiResponseAsync(string message)
  {
    //Формируем и отправляем запрос
    var request = new Body()
    {
      Model = model,
      Messages =
      [
        ..messages,
        new()
        {
          Role = "user",
          Content = message,
        }
      ],
      Stream = false
    };
    var json = JsonSerializer.Serialize(request, options);
    var content = new StringContent(json, Encoding.UTF8, "application/json");
    
    var apiResponse = await client.PostAsync(CHAT_URL, content);

    apiResponse.EnsureSuccessStatusCode();
    
    //Десериализуем ответ и сохраняем его для следующих отправлений
    var response = await apiResponse.Content.ReadFromJsonAsync<Models.Response.Response>(options);
    var responseMessage = response?.Choices.FirstOrDefault()?.Message?.Content ?? string.Empty;
    SaveMessage(message, "user");
    SaveMessage(responseMessage, "assistant");

    return responseMessage;
  }
}

После можно создать в Program.cs указанный класс и начать общаться с LLM:

var settings = new Settings()
{
  //...
};

using var client = new OpenAiClient(settings);

Console.WriteLine("Приложение запущено. Начните беседу (для выхода напишите 'exit'):");

while (true)
{
  Console.Write("> ");
  var input = Console.ReadLine();

  if (string.Equals(input?.Trim(), "exit"))
  {
    Console.WriteLine("Завершение работы программы.");
    break;
  }

  Console.WriteLine(await client.GetAiResponseAsync(input));
}

Теперь можно запускать и тестировать общение с llm в консоли! Да, это только поиграться, но можно так же и лучше познакомиться с работой с LLM.

Если есть много желания, то можно посмотреть код чуть подробнее в репозитории. Там есть стриминговое получение ответа, сжатие контекста, получение информации о текущем числе токенов.
